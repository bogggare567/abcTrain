# 011. i18n: a flat JSON string table per language, embedded via BinaryData

## Status

Accepted, implemented for a curated core-UI string set across 12
languages. Full tooltip/lesson-step translation is future work - see
"What's not covered" below.

## Context

The ask was full multilingual support (12 languages: en, ru, de, fr, es,
pt, zh-Hans, ja, ko, it, pl, uk) across every visible string in all four
plugins - game names/instructions, every parameter tooltip, every lesson
step, every button/label. That's several hundred long strings (the
tooltip rewrite in [decisions/010](010-book-library-scope.md) alone added
multi-sentence text per parameter) times 12 languages - translating all
of it to a quality worth shipping is its own large, separate effort.
This pass builds the real, working i18n *infrastructure* and translates
the bounded set of core UI strings (game names/instructions, common
labels/buttons) - not a placeholder, not fake, but deliberately scoped
smaller than "every string everywhere."

## Decision

**One flat JSON file per language** (`shared/i18n/strings/*.json`, e.g.
`ru.json`), each just `{"some.key": "translated text", ...}` - flat
dot-separated keys rather than nested JSON objects, since flat keys are
a single `var::getProperty()` call versus writing a path-walking nested
lookup for no real benefit here.

**Embedded via `juce_add_binary_data(I18nData SOURCES ...)`**, not read
from a filesystem path relative to the plugin binary - VST3/AU/Standalone
installs land in different OS-specific locations, and a plugin looking
for a sibling `strings/` folder next to itself is fragile across all of
them. `LocalisationManager::loadLanguageTable()` maps each language code
to its `BinaryData::xxx_json`/`xxx_jsonSize` symbol pair via an explicit
if-chain - `juce_add_binary_data`'s filename-sanitizing isn't a
predictable-enough transform (`zh-Hans.json` becomes `zhHans_json`, not
`zh_Hans_json` - the dash is dropped, not turned into an underscore) to
derive the symbol name programmatically from the language code.

**`LocalisationManager`** (`shared/i18n/LocalisationManager.h/.cpp`) is a
`juce::ChangeBroadcaster` constructed from a `juce::PropertiesFile&`
(same ownership pattern as `ProgressManager`): on first construction it
auto-detects the system language via `juce::SystemStats::getUserLanguage()`
(matching only the primary subtag, e.g. "en-GB" -> "en"; "zh" specifically
maps to "zh-Hans" since that's the only Chinese variant supported), falls
back to "en" if unsupported, and persists the choice - subsequent
construction reads the saved choice instead of re-detecting.
**`makeDefaultOptions()`** points at one shared `PropertiesFile` folder
("abcTrain", not per-plugin) so the language choice is a single
product-wide preference, not something to set separately in each of the
four plugins.

`getText(key)` falls back to the English table if the current language is
missing that key, and to the literal key string if English is missing it
too (so a missing translation is visibly obvious - a stray dotted key in
the UI - rather than silently blank). `getText(key, placeholders)` then
does simple `"{{name}}"` substitution over that result.

**A real bug caught before it shipped**: `getDisplayName()`'s first draft
embedded non-ASCII display names (Русский, 简体中文, 日本語, 한국어,
Українська) as raw hex-escaped `const char*` literals. `juce::String`'s
plain `const char*` constructor does **not** assume UTF-8 - a well-known
JUCE gotcha - so those literals came out as mojibake both in a test
comparison and (had it shipped) in the actual language picker. Caught by
a failing test comparing the switched-language `getText()` output against
an expected literal built the same fragile way, then fixed by wrapping
every non-ASCII display name in `juce::CharPointer_UTF8(...)` explicitly.
The JSON-loaded strings never had this problem, since
`loadLanguageTable()` already used the explicit `juce::String::fromUTF8
(data, size)` path.

**EarTrainer's editor is the reference integration**: a language
`ComboBox` in the title row (display names via `getDisplayName()`), and a
small `englishName -> i18n key` lookup table
(`translateGameName()`/`translateGameInstructions()` in
`Source/PluginEditor.cpp`) that maps each game's existing
`getName()`/`getInstructions()` English text to its key - chosen
specifically so the `Game` interface and all 9 game classes need **zero**
changes to become localizable; a game missing from that table (e.g. a new
one added before its i18n keys exist) just falls back to its raw English
text rather than breaking. `changeListenerCallback` only takes the
heavier "rebuild everything including the game-selector's items" path
when `LocalisationManager` itself is the broadcaster - taking that path
on every answer/progress tick too (not just a language switch) would
rebuild the combo box needlessly on every round played.

## What's not covered (deferred, tracked in roadmap.md)

- LearnerEQ/LearnerComp/LearnerVerb editors don't have a language
  selector yet - only EarTrainer does, as the reference integration.
- Parameter tooltip text (`ParameterGuide.h`/`ReverbGuide.h`/
  `FrequencyGuide.h`), all four lessons' step text, and each game's
  dynamic `getFeedbackText()` (which builds English sentences with
  runtime values baked in, e.g. "It was boosted at 3.2k Hz") are still
  English-only.
- Only the "reference integration" pattern (English-name -> key lookup
  table) exists for EarTrainer's games; nothing analogous wires
  LearnerComp/EQ/Verb's preset names or Bypass/Lesson button text through
  `LocalisationManager` yet.

## Consequences

- Every supported language is a real, loaded, tested JSON table - not a
  stub - for the core string set; `tests/LocalisationManagerTest.cpp`
  loads and checks non-empty output for all 12.
- Adding a 13th language is one new JSON file plus one line in
  `CMakeLists.txt`'s `juce_add_binary_data` call and one if-branch in
  `getBinaryDataFor()`/`getDisplayName()` - no `LocalisationManager` logic
  changes needed.
- The translations themselves (beyond English and Russian, which this
  session can vouch for directly) haven't been reviewed by a native
  speaker of each language - reasonable for short, unambiguous UI strings
  translated from their own original English, but worth a native-speaker
  pass before treating any of them as final, polished copy.
