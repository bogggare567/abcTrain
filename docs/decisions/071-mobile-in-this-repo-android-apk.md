# 071 — Мобильная версия остаётся в этом репозитории; Android собирается в CI

2026-10-29. Автор: «довести мобильную версию и, возможно, вынести её в отдельный репо для iOS, iPadOS и Android; подсказать, как установить». Выбрано: в этом же репо; iOS — сборка из Xcode; Android — APK в релизах.

## Почему не отдельный репозиторий

Мобильная версия — не другое приложение, а то же самое с другой раскладкой (ADR 060–062). Упражнения, звук, уроки, Live, строки на 12 языках — общий код, `compactLayout()` в одном и том же `PluginEditor`. Отдельный репозиторий копией разошёлся бы с первого исправления. Отдельный репозиторий с подмодулем требует каждое изменение делать в двух местах и двумя PR. Отдельным репозиторий станет, только если появятся страницы магазинов (описания, скриншоты для App Store и Google Play). Кода там не будет.

## iOS и iPadOS

- Сборка уже была (коммит «Первая сборка под iPhone и iPad»): `cmake -G Xcode -DCMAKE_SYSTEM_NAME=iOS`. Сюда влита ветка исправлений под симулятор iPhone 17: вырез, рамка окна, вкладки, единицы, ClickMap на пяти размерах в CI.
- Установка — своя сборка из Xcode с бесплатной подписью Personal Team. Работает 7 дней, потом пересобрать. Пошагово: `docs/wiki/Mobile.md`. TestFlight требует Apple Developer за $99 в год; это решение владельца, и к нему мы вернёмся, когда появятся тестировщики с iPhone.

## Android

У JUCE CMake нет цели Android, её умеет только Projucer. Вести `.jucer` руками значит держать второй список из ~90 исходников и шести наборов бинарных данных, который разойдётся с `CMakeLists.txt`. Поэтому `.jucer` **генерируется** из того, что знает CMake (`tools/android/make_jucer.py`):

- исходники — всё, что CMake компилирует в цель `EarTrainer`, без модулей JUCE;
- модули — те, что компилирует эта цель, плюс `juce_audio_plugin_client` для обёртки Standalone;
- бинарные данные — исходники, которые juceaide сгенерировал для каждой `juce_add_binary_data`, в своих пространствах имён, как на ПК;
- версия — `versions.json` → `app`, versionCode = major·10000 + minor·100 + patch.

Рабочий процесс «Android» на теге собирает Projucer из того же JUCE, сохраняет проект (появляется проект Gradle), собирает release-APK SDK и NDK раннера и прикладывает его к релизу.

**Подпись.** APK обновляются поверх друг друга только с одним ключом. Ключ хранится в секретах репозитория (`ANDROID_KEYSTORE_BASE64` и пароли; как создать — в `docs/wiki/Mobile.md`). Без секретов CI подписывает одноразовым ключом и предупреждает.

Код к Android уже был готов: проверки `JUCE_IOS || JUCE_ANDROID` (вход выключен, проверка обновлений молчит, платформа для Live). Хостинга плагинов на Android нет, curl тоже: сеть идёт через Java-реализацию JUCE.

## Что не проверено и как проверить

В облачном контейнере, где это писалось, нет Android SDK. Проверено, что проект генерируется и Projucer его принимает. Сборку APK проверит первый запуск рабочего процесса: Actions → Android → Run workflow на ветке. Если NDK найдёт несовместимость, она будет в журнале этого шага.
